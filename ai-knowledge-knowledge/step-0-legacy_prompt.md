【项目类型说明】本项目经结构探测确认为非 Java/Maven 项目（ACTUAL_MODULE_PREFIX=NON_JAVA）。
模板中涉及 Java 特有路径（如 pom.xml、-start/、-app/、-dao/、-client/ 等）和 Java 特有概念
（如 DubboReferenceConfig、MyBatis、ShardingSphere、RocketMQ 等）的扫描节，执行 Agent 应：
1. 识别该节的分析意图（如「提取外部依赖契约」、「还原数据模型」、「审计异步机制」等）；
2. 将意图映射到本项目实际存在的等价物（如 Shell/Python 脚本、配置文件、JSON 契约、CLI 工具链等）；
3. 对无等价物的扫描节明确标注「N/A：本项目无对应结构，原因：[一句话说明]」，不跳过、不虚构。
4. **工作区边界约束覆盖**：模板中所有「若 {{project_name}}-xxx/ 不存在 → 必须立即停止」的硬熔断指令，在 NON_JAVA 模式下**自动失效**，改为按上述第 1-3 条规则处理。禁止因 Java 路径不存在而触发熔断。
模板是引导分析思考的框架，不是死脚本，请充分发挥语义推断能力产出等深度的知识库内容。

我们正在为 ai-knowledge（ai-knowledge）构建 AI 可加载的项目知识库。旧文档可能存放在 old-readme/ 目录下。这些文档的内容未经代码验证,但包含有价值的领域线索。我们需要从中提取**仅与 ai-knowledge 相关的部分**,形成一份结构化的"声称清单",作为后续代码验真 的 checklist。

## 任务: 旧文档情报萃取

**第一步：探测目录**

使用 Read 工具列出 old-readme/ 目录，统计实际存在的文件。

- 如果目录不存在或为空：跳转至「空目录处理」
- 如果存在文件：按以下步骤逐文件读取至 EOF，提取涉及 ai-knowledge 的声称

**提取维度（对每个文件执行）**：

1. 服务定位声称：旧文档如何定义 ai-knowledge 的职责边界、业务定位
2. 对外接口声称：旧文档列出的所有 Dubbo 接口名、方法名、调用方
3. 数据模型声称：旧文档提到的所有表名、实体类名、字段
4. 业务链路声称：旧文档描述的经过 ai-knowledge 的业务流程
5. 下游依赖声称：旧文档声称 ai-knowledge 调用了哪些外部服务、哪些接口
6. 异步机制声称：旧文档提到的 Job、MQ Publisher/Listener、补偿机制
7. 风险与陷阱声称：旧文档标记的"常见坑/风险点"中涉及本服务的条目
8. 待确认项汇总：旧文档中所有标记为【待确认】且涉及本服务的条目

对每条声称,必须标注：
- 出处文件名
- 出处行号范围（如 L100-L143）
- 原文关键语句（不改写,保留原始措辞）

**空目录处理**：

如果 old-readme/ 不存在或为空，在产出文件顶部写入以下内容后直接输出 [!SUCCESS] 块：

```
> [!WARNING] 无旧文档
> old-readme/ 目录不存在或为空，本步骤跳过声称提取。
> 后续步骤的先验知识注入层将留空，直接基于代码事实构建知识库。
```

## 输出要求

1. 创建目录 ai-knowledge-knowledge/（如不存在）
2. 在该目录下生成 `Legacy_ai-knowledge_Claims.md`

**有旧文档时**：
- 文件顶部必须 have 警告框，明确声明"这些是旧文档声称，不是代码验证后的事实"
- 使用 8 个二级标题对应上述 8 个提取维度
- 每条声称用表格呈现：`| 声称内容 | 出处文件 | 行号 | 原文摘录 |`
- 只收录涉及 ai-knowledge 的内容，其他服务的声称一律不收录
- 如果某个类别无相关声称，显式标注"该类别无相关声称"

**无旧文档时**：只输出上方警告框，文件内容最简，不补充任何推测内容
