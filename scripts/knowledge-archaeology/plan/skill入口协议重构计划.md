# Skill 入口协议重构计划（最终版）

## 1. 背景

当前 `archaeology-commander` 的入口协议以 `旧文档=<有|无|path>` 为主锚点，并在 `SKILL.md` 中被定义为全局必填。该设计在只有 Step 0 legacy 萃取能力时成立，但在 Evolution Mode 成为正式能力后出现三类问题：

1. 用户第一次想跑增量演进时，不知道 `旧文档` 应如何填写。
2. `旧文档`（外部 legacy docs）与“已有知识库”（旧 MD）两类先验在认知上被混淆。
3. `ask_user` 组件失效，不能依赖图形化交互组件完成入口决策。

本计划的目标，是在不破坏主链编排的前提下，重构 `SKILL.md` 的入口层，让入口真正围绕用户任务意图工作，同时保留原有的强阻断能力。

---

## 2. 问题定义

### 2.1 当前入口的结构性问题

当前入口要求用户按以下格式启动：

```text
运行考古流水线 [项目名=<name>] 旧文档=<有|无|path> [工具目录=<path>]
```

这会导致：

- 用户被迫先理解内部实现，再表达任务意图。
- 合法的“无外部旧文档运行”场景被旧规则误伤。
- Evolution Mode 是隐式能力，用户无法从入口层直接理解自己正在做什么。

### 2.2 当前强验证规则的冲突点

现有规则把 `旧文档` 定义为全局必填字段；而新入口必须允许以下两类合法场景：

- 全量重建 + 不加载外部旧文档
- 增量演进 + 不加载外部旧文档

因此，如果不迁移强验证体系，入口重构将与现有约束直接冲突。

### 2.3 回归本源后的问题判定

本 plan 解决的不是“是否删除一个脚本文件”这种表象问题，而是以下已成立的架构治理问题：

1. `SKILL.md` 宿主化路径与历史 `run-archaeology.sh` 路径并存，会持续抬高维护成本。
2. 两条路径长期并存会制造认知混乱，难以判断哪条才是官方主线。
3. 长期继续背负脚本主线不符合 AI 宿主化、会话编排化的发展趋势。

但本问题的实施节奏仍取决于一个前置验证项：

- **`SKILL.md` 是否已足够在 Cursor 中独立运行**，必须通过分步验证确认。
- **antigravity 侧验证独立进行**，不与 Cursor 验证混为一谈。

因此，本 plan 的性质是：**问题已成立，但实施前必须先完成宿主独立运行验证。**
---

## 3. 目标

- **G1**：降低第一次启动时的认知门槛。
- **G2**：保留强阻断，不允许模糊降级或静默漂移。
- **G3**：完全不依赖 `ask_user`，仅通过普通对话文本完成收敛。
- **G4**：使入口分类严格 MECE。
- **G5**：改动集中在 `SKILL.md` 入口层，不重写主链与模板正文。
- **G6**：将原“旧文档强验证辅助约束”迁移为新的分层强验证体系，而不是直接删除。

---

## 4. 正式分类模型（MECE）

### 4.1 第一层：运行基底（一级入口）

一级入口只问一件事：

#### R1. 全量重建
- 不复用当前目录已有知识库
- 重新生成整套知识库

#### R2. 增量演进
- 复用当前目录已有知识库
- 在旧假说基础上覆写和补充

这两类互斥且穷尽，是严格 MECE 的一级分类。

### 4.2 第二层：外部旧文档策略（附加维度）

#### D1. 不加载外部旧文档
#### D2. 加载外部旧文档

该层与第一层正交，由此自然组合出 4 个运行态：

| 运行基底 | 外部旧文档 | 组合态 |
|---|---|---|
| 全量重建 | 否 | 纯全量 |
| 全量重建 | 是 | 全量 + legacy 验真 |
| 增量演进 | 否 | 纯增量 |
| 增量演进 | 是 | 增量 + legacy 混合 |

注意：这 4 种是组合态，不再作为一级并列选项。

## 5. 新入口协议

### 5.1 启动意图识别

以下输入都进入入口收敛流程：

- `运行考古流水线`
- `知识库考古`
- `开始考古`
- `启动知识库考古`
- 历史格式：`运行考古流水线 旧文档=...`

### 5.2 入口收敛流程

在真正进入 Preflight 之前，必须先进行纯文本收敛。**该收敛流程必须严格按顺序执行，不允许跳步、不允许忽略、不允许在未完成收敛时提前进入 Preflight。**

这是结合 Gemini CLI 当前设计得出的硬约束：由于 `ask_user` 组件失效，入口只能依赖普通对话中的多轮文本决策；一旦顺序执行被破坏，指挥官就无法稳定判断当前回复对应哪一轮问题，整个入口协议会立刻失去确定性，设计将全盘崩溃。

#### 固定顺序（不可打乱）

1. 读取 `config.json` 与显式参数，确定 `PROJECT_NAME`、`OUTPUT_DIR`、`AI_KNOWLEDGE_HOME`
2. 基于已确定的 `OUTPUT_DIR` 探测 `KNOWLEDGE_BASE_EXISTS`
3. 收敛运行基底（全量重建 / 增量演进）
4. 收敛旧文档策略（不加载 / 加载）
5. 如需加载旧文档，则继续收敛旧文档路径
6. 输出运行确认摘要
7. 仅在以上步骤全部完成后，方可进入 Preflight

#### 启动收敛状态机（最小模型）

为保证多轮对话在 Gemini CLI 中可持续推进，入口必须显式遵守以下状态机：

- `STARTUP_PENDING_RUN_BASE`：等待确认运行基底
- `STARTUP_PENDING_LEGACY_MODE`：等待确认旧文档策略
- `STARTUP_PENDING_LEGACY_PATH`：等待提供旧文档路径
- `STARTUP_READY`：所有必要信息已收敛完成，可进入 Preflight
- `STARTUP_CANCELLED`：用户取消或本轮启动终止

#### 状态转移规则

- 识别到启动意图后，进入 `STARTUP_PENDING_RUN_BASE`
- 运行基底确认完成后，进入 `STARTUP_PENDING_LEGACY_MODE`
- 若旧文档策略选择“加载”，进入 `STARTUP_PENDING_LEGACY_PATH`
- 若旧文档策略选择“不加载”，直接进入 `STARTUP_READY`
- 路径校验通过后，进入 `STARTUP_READY`
- 用户明确表示取消、停止、稍后再说时，进入 `STARTUP_CANCELLED`
- 用户在任意中间状态重新发送新的启动命令时，必须丢弃旧状态并从 `STARTUP_PENDING_RUN_BASE` 重新开始

#### 异常回复处理

- 若用户回复与当前状态无关的内容，禁止进入下一步，必须重复当前问题
- 若用户在等待路径时回复 A/B 之外的普通说明文字，且无法解析为路径，必须提示“当前正在等待旧文档路径”
- 若用户在任一步骤答非所问，不得自行脑补其意图

#### 机制生效保障（硬约束）

本方案的可行性建立在“入口选项收敛机制必须稳定生效”这一前提上。该机制不是提示性辅助交互，而是新的唯一准入门。

必须满足以下硬约束：

1. 未完成运行基底收敛前，禁止进入 Preflight
2. 未完成旧文档策略收敛前，禁止进入 Preflight
3. 若当前回复无法归约为当前状态允许的选项，必须停留在当前状态并重复提问
4. 不得对未明确收敛的选项使用默认值
5. 不得猜测用户意图以绕过当前状态
6. 不得因交互失败、回复模糊或状态丢失而自动继续主流程
7. 若入口状态机未到达 `STARTUP_READY`，本次启动视为未成立

结论：选项机制若未稳定生效，则本轮启动必须卡住或终止，不得降级为“先跑再说”。

#### Step 1：确认运行基底

```text
检测到你正在启动知识库考古流水线。

请确认本次运行方式：
A. 全量重建（忽略现有知识库，从代码事实重新生成）
B. 增量演进（基于现有知识库继续更新）

请直接回复 A / B。
```

#### Step 2：确认旧文档策略

```text
是否加载外部旧文档作为声称来源？
A. 不加载
B. 加载，请下一条消息提供路径

请回复 A / B。
```

#### Step 3：条件校验

- 若选择“加载外部旧文档”，则路径条件必填。
- 若选择“增量演进”，则必须存在已有知识库。
- 任一条件不满足时立即阻断。

#### Step 4：运行确认摘要

执行前必须输出：

```text
本次运行确认如下：
- 运行基底：全量重建 / 增量演进
- 外部旧文档：无 / <path>
- 现有知识库：存在 / 不存在
- 增量模式：启用 / 禁用
- Step 0：执行 / NO_DOCS
```

### 5.3 输入归约（Normalization）规则

由于 Gemini CLI 下的入口依赖自然语言多轮对话，必须对用户回复做最小归约，避免协议脆弱化。

#### 运行基底问题的归约规则

以下输入都归约为 `A / 全量重建`：
- `A` / `a`
- `全量`
- `全量重建`
- `重新生成`
- `不要旧知识库`

以下输入都归约为 `B / 增量演进`：
- `B` / `b`
- `增量`
- `增量演进`
- `继续更新`
- `基于现有知识库`

#### 旧文档策略问题的归约规则

以下输入都归约为 `A / 不加载旧文档`：
- `A` / `a`
- `不加载`
- `无旧文档`
- `不用`

以下输入都归约为 `B / 加载旧文档`：
- `B` / `b`
- `加载`
- `有旧文档`
- `要加载`

#### 无法归约时的处理

- 无法明确归约时，必须重复当前问题
- 不得因“看起来差不多”而自动推进状态机
- 不得跳过当前状态直接进入 Preflight

### 5.4 历史输入兼容与优先级

为保证平滑过渡，历史格式仍可兼容，但其优先级必须固定。

#### 兼容输入

```text
运行考古流水线 旧文档=无
运行考古流水线 旧文档=/path/to/docs
```

#### 固定优先级

1. 先读取 `config.json`
2. 再解析显式参数：`项目名=`、`工具目录=`、`旧文档=`
3. 再推导 `PROJECT_NAME` 与 `OUTPUT_DIR`
4. 再探测 `KNOWLEDGE_BASE_EXISTS`
5. 再收敛缺失的入口决策（尤其是 `RUN_BASE`）

#### 兼容映射规则

- `旧文档=无` → `LEGACY_MODE=NO_DOCS`
- `旧文档=/path` → `LEGACY_MODE=WITH_DOCS`，并将该路径作为候选 `LEGACY_PATH`
- 若历史输入已给出 `旧文档=...`，则跳过“是否加载旧文档”的提问，但仍必须完成 `RUN_BASE` 收敛
- 历史输入不得绕过新的顺序执行机制；缺失的一级决策仍必须补齐

## 6. 强验证体系迁移

### 6.1 废弃的旧规则

以下旧规则应删除原始形态：

- `旧文档` 作为全局必填字段
- `旧文档` 缺失即全局停止

### 6.2 新的强验证体系

#### V1. 运行基底必答
未确认“全量重建 / 增量演进”前，禁止进入 Preflight。

#### V2. 旧文档策略必答
未确认“加载 / 不加载旧文档”前，禁止进入 Preflight。

#### V3. 旧文档路径条件必填
仅在选择“加载外部旧文档”时要求路径：
- 缺路径 → 停
- 不可读 → 停
- 越界 → 停

#### V4. 现有知识库条件必需
仅在选择“增量演进”时要求已有知识库存在：
- 未探测到旧知识库 → 停
- 严禁自动降级为全量重建

#### V5. 合法的无旧文档运行不得误伤
以下两类运行必须合法：
- 全量重建 + 不加载旧文档
- 增量演进 + 不加载旧文档

### 7.3 需要保留但改写的逻辑

以下旧输入仍可兼容：

```text
运行考古流水线 旧文档=无
运行考古流水线 旧文档=/path/to/docs
```

映射策略：
- `旧文档=无` → `LEGACY_MODE=NO_DOCS`
- `旧文档=/path` → `LEGACY_MODE=WITH_DOCS`

如果未显式收敛运行基底，则仍需继续询问“全量重建 / 增量演进”。

#### K2. 工具根目录解析
`AI_KNOWLEDGE_HOME` 的优先级保持不变。

#### K3. 项目名与输出目录推导
现有 `PROJECT_NAME`、`OUTPUT_DIR` 推导规则保持不变。

#### K4. 时间戳、日志目录、模型配置
保持不变。

#### K5. Step 0 的 NO_DOCS 语义必须固定
当 `LEGACY_MODE=NO_DOCS` 时，不执行 Step 0 的旧文档扫描逻辑；而是直接生成 NO_DOCS 版 `Legacy_${PROJECT_NAME}_Claims.md`，并将其视为 Step 0 的合法短路完成。

这意味着：
- Step 0 在语义上已闭环
- 但不会再进入真实的旧文档遍历流程
- `SKIP_STEP0=true` 的现有实现语义保留，不做反向重构

#### K6. 工作区边界不放宽
本次改造不放宽旧文档工作区边界限制。若用户希望加载工作区外文档，必须先将文档复制或纳入当前工作区，再作为合法路径输入。

### 7.4 需要调整的段落：§二“前置检查 (Preflight)”

#### P1. 新增已有知识库探测结果变量
在交互前或最晚进入 Preflight 前，探测：

```text
KNOWLEDGE_BASE_EXISTS = true | false
```

#### P2. 修改旧文档路径验证条件
从“只要有 LEGACY_PATH 就验证”，改成：
- 仅当 `LEGACY_MODE=WITH_DOCS` 时才进行旧文档路径校验

#### P3. 修改 Evolution Mode 启用条件
从“探测到 md 文件就启用”，改成：
- 仅当 `RUN_BASE=EVOLUTION` 且 `KNOWLEDGE_BASE_EXISTS=true` 时正式启用 `EVOLUTION_MODE=true`

#### P4. 增量模式失败不得降级
若：
- `RUN_BASE=EVOLUTION`
- 但 `KNOWLEDGE_BASE_EXISTS=false`

则必须立即停止，不得自动切回全量。

### 7.5 需要新增的入口阻断文案

#### 阻断文案 1：未完成运行基底确认

❌ 尚未确认本次运行方式，流水线不能启动。

```

#### 阻断文案 2：未完成旧文档策略确认

```

#### 阻断文案 3：增量演进缺少现有知识库
```text

当前目录未检测到可复用的知识库产物，因此不能基于现有知识库继续更新。
请改选全量重建，或先生成基准知识库。
```

#### 阻断文案 4：旧文档策略为加载，但未提供有效路径
```text
❌ 已选择加载外部旧文档，但未提供可读路径。
请提供有效路径，否则本次启动终止。
```

## 8. 必须保留的红线

### R1. 审计硬熔断
`[!SUCCESS]` 缺失必须停止。

### R2. 变量闭环
任何模板变量未替换完成不得运行。

### R3. 物理隔离
执行 Agent 仍禁止带 `-r` / `--resume`。

### R4. 上下文保护
指挥官仍不能直接读大日志，必须做摘要提取。

### R5. 路径安全
旧文档路径验证仍必须保留工作区边界限制。

### R6. 增量模式不得静默降级
选择增量演进但无旧知识库时，必须停止。

### R7. 运行确认摘要必须输出
这是新的协议透明化红线。

## 11. 实施步骤

### Phase 0：问题成立但先验证

### Phase 1：Cursor 宿主独立运行验证
按最小可证伪顺序逐步验证，每项必须单独记录结果。Cursor 是主验证线，用于判断 `SKILL.md` 是否可作为未来唯一主线候选。

1. **V-C1：子进程孵化验证**
   - 验证宿主中的 001 是否可调用 `gemini -p '' --yolo` 子进程
   - 验证失败则本 plan 暂停进入实施阶段

2. **V-C1b：宿主 shell 工具链能力验证**
   - 验证宿主可稳定执行多次 shell 调用，而非仅一次性拉起子进程
   - 至少覆盖：`jq`、`cp`、重定向、`grep`/`head`、工作目录解析
   - 若这些工具链能力不稳定，则不得宣告宿主主线成立

3. **V-C2：文件系统与日志验证**
   - 验证可写 `next-prompt.md`
   - 验证可写 `.logs/` 与步骤日志
   - 验证协议复制与输出目录初始化可执行

4. **V-C2b：宿主授权/拦截模型验证**
   - 验证 shell、文件写入、日志归档过程中是否触发权限确认或额外拦截
   - 验证权限确认是否会打断多轮状态机
   - 验证同一轮会话中的多次 shell / 文件写入行为是否一致

5. **V-C3：入口状态机验证**
   - 验证 `STARTUP_PENDING_*` 多轮文本状态机在 Cursor 中稳定生效
   - 验证“无法归约则卡住”“重新发起则重置”“取消则终止”

6. **V-C4：分层主链验证**
   - **Smoke 层**：至少验证 Step 0 / Step 1 可跑通
   - **Relay 层**：验证 `[!SUCCESS]` 摘要提取与跨步骤接力有效

### Phase 2：验证结论分流

#### Case C1：可孵化 Gemini 子进程
预期：
- Cursor 中的 001 可成功执行 `gemini -p '' --yolo`
- 不因宿主限制而被拒绝

#### Case C1b：宿主 shell 工具链可持续使用
预期：
- 除孵化子进程外，宿主还能稳定执行 `jq`、`cp`、重定向、`grep`/`head`、工作目录解析等命令
- 多次 shell 调用结果一致，不出现“第一次可用、后续被拦截”的漂移

#### Case C2：可写运行时文件
预期：
- 可写 `${OUTPUT_DIR}/.tmp/next-prompt.md`
- 可写 `${OUTPUT_DIR}/.logs/` 与步骤日志
- 可完成协议复制与输出目录初始化

预期：
- shell、文件写入、日志归档过程中的权限确认可预测
- 不会因宿主弹确认或附加拦截导致多轮状态机漂移
- 若被拦截，失败信号可被 001 明确识别，而不是静默吞掉

- `STARTUP_PENDING_RUN_BASE`、`STARTUP_PENDING_LEGACY_MODE`、`STARTUP_PENDING_LEGACY_PATH` 可稳定停留与推进

#### Case C4-S：Smoke 层主链验证

#### Case C4-R：Relay 层接力验证
预期：
- `[!SUCCESS]` 可被稳定提取
- `LAST_SUMMARY` 可跨步骤注入并驱动下一步

#### Case C4-M：Module 层循环验证
预期：
- 至少一次 Step 08 单模块循环可执行

#### Case 6：标准两轮收敛
场景：
- 用户输入 `运行考古流水线`
- 第一轮回复 `A`
- 第二轮回复 `B`
- 第三轮提供合法路径

预期：
- 状态机依次经过 `STARTUP_PENDING_RUN_BASE` → `STARTUP_PENDING_LEGACY_MODE` → `STARTUP_PENDING_LEGACY_PATH` → `STARTUP_READY`

场景：
- 用户回复“我选增量”
- 用户回复“不要旧文档”

预期：
- 按 normalization 规则正确归约
- 不因回复形式变化破坏顺序执行

#### Case 8：答非所问
场景：
- 当前正在等待运行基底确认，但用户回复“帮我顺便看下 README”

预期：
- 不推进状态机

场景：
- 已进入 `STARTUP_PENDING_LEGACY_MODE`

- 丢弃旧状态
- 从 `STARTUP_PENDING_RUN_BASE` 重新开始

场景：
- 用户回复“取消”“停止”“稍后再说”

预期：
- 状态机进入 `STARTUP_CANCELLED`
- 本轮不进入 Preflight

### 12.3 失败分类与分流

#### F1：宿主能力失败
表现：
- 无法稳定 shell
- 无法写文件
- 无法孵化执行 Agent

结论：
- 当前宿主主线不成立
- 停止推进“统一主线”实施

#### F2：协议实现失败
表现：
- 状态机错乱
- 未完成收敛即进入 Preflight
- 归约规则在真实对话中不稳定

结论：
- 问题仍成立
- 但需先修正 `SKILL.md` 协议实现，不能归咎于宿主能力

#### F3：执行链路失败
表现：
- `[!SUCCESS]` 提取不稳
- `LAST_SUMMARY` 接力失效
- Step 08 模块循环挂起或日志链断裂

结论：
- 宿主可能成立
- 但 orchestrator 机制仍未闭环，不得宣告主线收敛完成

### 12.4 成功判据

以下条件同时满足，才视为入口协议改造通过：

1. Cursor 侧宿主独立运行前置验证全部通过
2. Cursor 至少通过 Smoke、Relay、Module 三层主链验证
3. 进入 Preflight 前，必须已输出一次运行确认摘要
4. `RUN_BASE`、`LEGACY_MODE`、`EVOLUTION_MODE` 与用户最终选择一致
5. 不存在 silent fallback（尤其是增量失败后自动切全量）
6. 历史命令输入不会再触发旧的“旧文档缺失即停”错误
7. 多轮交互中，任何一步未完成时都不得提前进入 Preflight
8. antigravity 侧验证结果需单独记录，不得直接拿 Cursor 结果替代
9. 若要宣告“双宿主可用”，则 antigravity 必须单独满足 A1~A4

### 12.5 Cursor 初轮实测结果（2026-04-08）

#### 已取得的正向证据

1. **宿主等待慢速子进程：通过**
   - 已实测 12s、35s 的慢 shell 命令可被 Cursor 正常等待至返回
   - 已实测慢速 `gemini -p '' --yolo` 调用可被 Cursor 等待至完成，不存在“宿主提前放弃”现象

2. **慢速 Gemini + 日志回传链：通过**
   - 已实测将慢速 Gemini 输出重定向到日志文件
   - 已成功从日志中提取 `[!SUCCESS] OK`
   - 说明“慢速执行 → 日志落地 → 摘要提取”链路在 Cursor 中成立

3. **宿主机械前提：通过**
   - `gemini`、`jq`、`python3` 可用
   - 文件重定向、`cp`、`grep | head`、日志目录写入可用
   - `05_module_manifest.json` 可被 `jq` 成功读取

#### 已观测到的非阻塞风险

1. **Gemini CLI 前置行为噪音**
   - 个别慢速调用中，即使明确要求“不调用工具”，仍出现 `list_directory` 尝试
   - 当前未破坏 `[!SUCCESS]` 提取，因此暂记为中风险噪音，而非阻塞项

2. **模型容量波动（429）**
   - 慢速 Gemini 调用中出现过 `MODEL_CAPACITY_EXHAUSTED` / 429
   - 该问题在自动 backoff 后仍可成功返回，初步判断为模型服务侧波动，而非 Cursor 宿主等待失败

#### 当前结论

- Cursor 侧的主要风险已不再是“是否能等待慢速 Gemini 回传”
- 当前更应关注：
  1. Gemini CLI 的前置规则加载/工具尝试是否会污染真实主链
  2. 模型容量波动是否需要显式纳入失败分流
  3. 真实多轮收敛状态机是否会在宿主连续对话中被过度推进

## 13. 最终结论

本次入口协议重构是必要改造，而不是文案修补。最终结构为：

- 一级入口：运行基底（全量重建 / 增量演进）
- 二级维度：旧文档策略（加载 / 不加载）
- 强验证：决策必答 + 条件必填 + 条件必需
- 实现落点：重写 `SKILL.md` §一、调整 §二、保留主链不动

该方案严谨、MECE、可落地，且能完整替代旧的“`旧文档` 全局必填”逻辑。
